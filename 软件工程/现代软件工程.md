# 1 软件及软件工程
## 什么是计算机软件
计算机软件是指计算机系统中的程序、数据及其相关文档
- 程序：按特定顺序组织的计算机数据和指令集合
- 数据：是程序正常执行的数据结构
- 文档：与开发、维护、使用有关的资料

软件的特点
- 逻辑复杂度高
- 成本高
- 复制成本低

软件的分类
- 系统软件：最靠近硬件的一层
- 支持软件：支持软件开发和维护的软件，DBMS
- 应用软件

软件技术演化
- 程序设计阶段
- 程序系统阶段
- 传统软件工程阶段
- 面向对象阶段

软件发展趋势：**一切都会软件化、智慧化**
## 软件危机
原因：软件系统规模变大，复杂程度变高，软件可靠性问题突出
原始软件生成方式无法满足计算机软件需求，导致软件开发和维护过程中一系列严重问题

软件危机的表现：
- 对软件开发进度、成本估算不准
- 无法满足用户需求
- 质量不可靠
- 难以更改、调试、增强
- 没有合适的文档
- 成本比重上升
- 软件开发效率跟不上计算机应用深入的趋势

### 软件危机产生的原因

与软件本身特点有关，软件具有：
- 逻辑复杂
- 不可见
- 难以度量
- 难以维护
- 需求容易变化
- 开发成本和进度难以估算
这些特点给软件开发和维护带来了客观困难。

与开发和维护方法不正确有关
主要问题包括：
- 把软件简单等同于程序
- 急于求成，缺乏系统规划
- 个体化开发方式严重
- 各自为政，没有统一的方法学
- 没有规范的软件开发和维护过程
重要观点：
**软件开发不等于直接编程**
编程只占软件开发工作量的一小部分，真正的软件开发还包括需求分析、设计、测试、维护、管理等大量工作。

解决软件危机的途径
要解决软件危机，必须同时采取：
- **技术措施**：使用先进的软件开发方法、工具和技术
- **管理措施**：加强组织管理、过程控制、质量保证和项目管理
软件工程就是为了解决软件危机而产生的学科。

## 软件工程定义
**软件工程是指导计算机软件开发和维护的一门工程学科**
它将工程的概念、原理、技术和方法应用到软件开发中，目标是：
1. 经济地开发软件
2. 开发高质量软件
3. 有效维护软件

软件工程的三要素：
- 方法：面向对象方法学、传统方法学等
- 工具：编码、测试、维护等
- 过程：活动时间、参与人员等

软件质量可以从以下方面理解：
- **正确性**：程序操作符合规格说明的程度
- **可维护性**：程序经受变化的能力
- **完整性**：程序不受外界攻击影响的程度
- **可用性**：程序容易被用户使用的程度
- **可扩展性**：软件适应未来扩展和变化的能力

软件开发的主要框架活动包括：
- 沟通
- 策划
- 建模
- 需求分析
- 设计
- 构建
- 编码
- 测试
- 部署

软件普适性活动
- 软件项目跟踪和控制
- 风险管理
- 软件质量保证
- 技术评审
- 测量
- 软件配置管理
- 可复用管理
- 工作产品的准备和生产

## 软件生命周期
生命周期由三个时期组成：
- 软件定义
- 软件开发
- 运行维护

软件定义时期：
- 问题定义：要解决什么问题、明确工程目标
- 可行性研究：判断问题是否有解决方法等
- 需求分析

软件开发时期：
- 总体设计又称概要设计
- 详细设计又称模块设计
- 编码和单元测试
- 综合测试包括集成测试和验收测试

运行维护时期：主要任务是使软件持久地满足用户需求

# 2 软件工程师及软件团队
## 软件工程师
软件工程师应该具备的特质：软件工程师不仅要会写代码，还要具备良好的职业素养和工程意识

**程序员不是只会写代码的人，还要能读代码、测代码、改代码、管代码**

在软件工程中，单个成员被称为 IC：Individual Contributor
个人工作的质量直接影响产品质量

## 软件团队
真正的软件团队具有
- 共同目标
- 成员之间互相依赖
- 成员之间协作完成任务

团队的特点包含：
- 有一致的集体目标
- 团队成员共同完成目标
- 成员不一定同时工作，但目标是一致的
- 成员有各自分工
- 成员之间互相依赖、合作
- 团队任务的完成依赖整体协同

团队的组织模式
- 封闭模式
	- 遵循传统权力层级
	- 管理结构清晰
	- 控制性较强
	- 创新性可能较弱
- 随机模式
	- 团队较松散
	- 依靠成员个人自发性
	- 创新性较强
	- 管理和控制较弱
- 开放模式
	- 兼具封闭模式的可控性
	- 也具有随机模式的创新性
	- 是一种折中型团队结构
- 同步模式
	- 依赖问题的自然划分
	- 成员之间不需要大量交流
	- 各成员可以相对独立地解决不同部分问题

## 代码规范
**代码首先是给人看的，其次才是给机器执行的**
代码规范可以提高：
- 可读性
- 可理解性
- 可测试性
- 可维护性
- 可修改性
- 团队协作效率

代码规范
- 程序文档化
- 语句构造
- 数据说明
- 输入/输出

### 源程序文档化
- 标识符命名
- 注释
- 程序的视觉组织
#### 标识符命名
匈牙利命名法
- 前缀表示变量类型
- 后面表示变量含义
- 单词首字母大写
```
int iMyAge;  
char cMyName[10];  
float fManHeight;
```
小驼峰命名法
- 第一个单词首字母小写
- 后面单词首字母大写
```
int myAge;  
char myName[10];
```
大驼峰命名法
- 每个单词首字母都大写
```
int MyAge;
```
下划线命名法：单词之间用下划线
#### 注释
- 序言性注释：序言性注释通常放在每个程序模块开头
- 功能性注释：功能性注释通常嵌在源程序体内，用来描述程序段功能

#### 程序的视觉组织
是通过空格、空行、缩进、括号让程序结构更清晰

### 数据说明
为了让程序中的数据说明更容易理解和维护，应采用规范风格。
- 数据说明次序规范化
- 说明语句中变量安排有序化
- 使用注释说明复杂数据结构

### 语句构造
- 一行只写一条语句
- 适当添加空格
- 让程序逻辑更清楚
### 输入和输出
输入规范：
- 对所有输入数据进行检验
- 识别错误输入，保证数据有效性
- 检查输入项重要组合的合理性
- 必要时报告输入状态信息
- 输入步骤和操作尽可能简单
- 保持简单输入格式
- 允许自由格式输入
- 允许使用缺省值
- 输入一批数据时，最好使用输入结束标志，而不是让用户指定数据数目

交互式输入规范
- 屏幕上应有明确提示符
- 指明可选项种类
- 指明取值范围
- 输入过程中给出状态信息
- 输入结束时给出状态信息

输出规范
- 所有输出都应加注解
- 输出报表应设计良好
- 输出内容应清晰、易理解

### 代码复审
代码复审也叫代码评审，是指通过阅读代码检查：
- 源代码是否符合编码标准
- 代码质量是否达标

代码复审的目的包括：
- 在项目早期发现缺陷，降低损失
- 发现编码错误
- 发现不符合代码规范的地方
- 发现逻辑错误
- 发现算法错误
- 发现潜在错误
- 发现回归性错误
- 发现可改进之处
- 促进团队沟通
- 促进知识共享
- 推动团队共同提高

代码复审的内容
- 代码是否符合规范
- 是否进行了错误处理
- 代码可读性如何
- 注释是否足够
- 是否有无用代码可以删除
- 性能如何
- 最坏情况表现如何
- 循环中是否有明显可优化部分
- 系统调用和网络调用是否可能超时
- 超时如何处理

### 结对编程
结对编程是敏捷软件开发中的一种方法
指的是两个程序员在一台计算机上共同工作

输入代码的人叫 driver
审查代码的人叫 navigator/observer

## 代码测试
大多数软件是多人合作完成的，所以每个程序员都应该测试自己的代码，让自己写的模块尽量可靠
### 单元测试
对软件中的最小可测试单元进行检查和验证
常见单元包括：函数、类、组件

### 回归测试
修改旧代码后，重新进行测试，以确认修改没有引入新的错误，也没有导致其他代码出错
回归测试特点：
- 最好自动化
- 应该能在每次构建后快速运行
- 用来尽早发现问题
- 单元测试是回归测试的基础

### 测试驱动开发 TDD
在编写某个功能的代码之前，先编写测试代码，然后只编写能让测试通过的功能代码，通过测试推动开发
TDD 类似于砌墙前先拉好线，之后所有砖都按照这条线砌
TDD 有助于：
- 编写简洁代码
- 编写可用代码
- 提高代码质量
- 加快开发过程
- 减少缺陷
## 程序调试
软件调试是在成功测试之后开始的工作，是为了**进一步诊断和改正程序中的潜在错误**

调试活动包括
- 确定程序中可疑错误的确切性质和位置
- 修改程序的设计或编码，排除错误

调试步骤
- 从错误的外部表现入手，确定程序中出错的位置
- 研究相关部分的程序，找出错误的内在原因
- 修改设计或代码，排除错误
- 重新执行暴露该错误的原始测试
- 必要时执行相关测试，确认没有引入新问题

调试工具包括：
- 单步追踪
- 断点：程序运行到指定位置时暂停
	- 代码断点
	- 数据断点
## 版本控制
如果没有版本控制会出现
- 文件版本越来越多
- 不知道哪个是最新版本
- 想找回旧内容却找不到
- 不敢删除旧文件
- 多人协作时难以合并修改
- 不知道谁改了什么
- 版本同步困难
版本控制指的是对软件开发过程中文件变更的管理

## 过程模型
**传统过程模型**
- 写了再改模型
- 瀑布模型
- 增量过程模型
- 演化过程模型
	- 原型开发模型
	- 螺旋模型
	- 并发模型
**专用开发模型**
- 基于构件的开发
- 面向方面的开发

### **瀑布模型**
将软件生命周期划分为：软件计划、需求分析、设计、实现、测试、运行和维护，自上而下相互衔接的固定次序，如瀑布一样

变体：v 模型 ![[Pasted image 20260518105503.png]]

特点：
- 阶段间有顺序性和依赖性
- 推迟实现的观点
- 质量保证的观点

优点：
- 强迫开发人员采用规范方法
- 每个阶段交出的产品必须经过质量保证小组仔细检验
- 严格规定每个阶段必须提交的文档
- 瀑布模型成功很大程度是由于它基本上是文档驱动

缺点：
- 难以应对需求变化
- 过于理想：实际过程难以按照顺序
- 风险太大：用户须等系统开发完才能见到软件
- 阻塞状态：开发者常常被不必要耽搁

适合项目：
- 需求相当稳定
- 开发团队对应用领域熟悉
- 外部环境不可控因素少
- 小型清晰的项目

### 原型开发模型（快速原型）
原型是预期系统的可执行版本，相当于可以在它基础上自由扩展

一个原型不用满足目标软件所有约束，其目的是能快速、低成本构建原型
原型交给客户试用，再收集意见迭代下一个原型 ![[Pasted image 20260518110358.png]]
优点：
- 快速开发出可以演示的系统，方便了客户沟通
- 采用迭代技术能使开发者逐步弄清客户需求

缺点：
- 用户误解原型应该与真实系统一样
- 缺少项目标准
- 缺少控制，用户会不断提出要求，原型迭代周期难控制
- 额外花费
- 运行效率会受到影响
- 原型法需要开发者与用户密切接触，有些是不允许的

原型的使用策略：
- 废弃策略：用于探索性和实验型原型开发。根据实验结果良好的结构和设计思想重新设计目标
- 追加策略：用于演化型原型开发，这种原型是实现了目标系统中已明确定义的特性的一个子集，通过对它不断修改补充演化为最终的目标

适用项目：
- 需求不明确
- 需求容易变化

### 螺旋模型
风险驱动的软件开发模型，主要针对大型项目
- 采用循环的方式加深系统定义和实现
- 确定一系列里程碑
- 第一圈一般开发出产品规格说明，接下来每次迭代完善

结合了原型的迭代和瀑布模型的可控性、系统性
每个阶段之前都增加了风险分析的过程 ![[Pasted image 20260518111419.png]]

优点：
- 结合迭代性质和瀑布模型系统性和可控性，是一种风险驱动的模型
- 循环方式逐步加深系统定义和深度，降低风险，更好理解
- 确定一系列里程碑，确保各方面都有可行的系统解决方案
- 始终保持可操作性
- 风险驱动

缺点：
- 依赖大量风险评估专家
- 软件开发人员需要擅长寻找可能风险，准确分析风险，否则会带来更大风险
- 增加了风险管理成本

### 并行模型
![[Pasted image 20260518112115.png]]
- 适用于不同团队共同开发
- 可以表示为一系列活动和对应的状态
- 定义了一系列事件，事件将触发工程活动、动作或者任务状态的转换

### 增量模型
以迭代的方式运用瀑布模型，随时间推移，发布一系列称为增量的版本，每个版本为用户提供更多功能

增量模型把待开发的系统模块化，然后每个模块使用小瀑布模型
![[Pasted image 20260518112613.png]]
![[Pasted image 20260518112631.png]]

使用方法：
- 第一个增量一般是核心产品，满足基本需求
- 每个增量都提交一个可以操作的产品
- 用户使用上一个增量的提交物评价，制定下一个增量计划
- 重复上述过程到最终产品生产

优点：
- 提高对用户需求响应
- 人员分配灵活
- 可规避技术风险

缺点：
- 每个附加增量并入时，不能破坏原来的东西
- 加入增量应简单方便
- 无法处理需求发生变更的情况
- 难以确定所有版本共需的公用模块

适合的项目：
- 基本明确需求
- 对市场和用户把握需要逐步了解
- 需要一步一步实施，模块分批交付

### 专用开发模型
基于构件的开发---能使软件复用
形式化方法---注重需求的数学规格说明
面向方面的软件开发---为定义、说明、设计和构件方面提供过程和方法

- 缺乏通用构件组装结构标准
- 构件可重用性和系统高效性之间不协调
- 过分依赖构件，构件质量会影响最终产品质量

# 4 敏捷流程
非敏捷-瀑布式开发
缺陷：
- 程序维护成本越来越高
- 团队氛围压抑
- 不方便变更需求

敏捷开发遵循软件客观规律，不断进行迭代增量开发，最终交付符合客户价值的产品
敏捷宣言：
- 个体和交互胜过过程和工具
- 可以工作的软件胜过面面俱到的文档
- 客户合作胜过合同谈判
- 响应变化胜过遵循计划

基于敏捷原则进行的软件开发过程，视为敏捷过程
- **极限编程**
- **Scrum**

## 极限编程
极限编程主要目标在于降低因需求变更而带来的成本
采用迭代的交付方式，每个迭代很短

极限编程实施原则
- 快速反馈
- 假设简单
- 包容变化

极限编程过程
- XP 策划
	- 建立待开发软件必要特征的用户故事
	- 评估每个故事给出时间成本（周）
	- 故事分组并置于要开发的下一个软件增量中
	- 第一个版本发布后 xp 团队计算项目速度
- XP 设计
	- 按照 keep it simple 原则
	- 在某个故事遇到困难时，立即建立可执行原型
- XP 编码
	- 鼓励测试驱动开发、结对编程、重构
- XP 测试
	- 每天进行集成和确认测试
	- 验收测试由客户确定

## Scrum
一种敏捷开发的模型，采用短周期迭代的交付方式

Scrum 流程包括 3 个角色、3 个工件、5 个活动
一个 sprint 为 2-4 周，从计划会开始到回顾会议结束为一次 sprint，有严格的时间控制

角色
- Scrum 主管：同项目经理类似，负责维护过程和任务
- 产品负责人
- 开发团队
工件
- 产品订单
- 冲刺订单
- 燃尽图![[Pasted image 20260518151502.png]]
活动
- Sprint 冲刺
- 冲刺计划会
- 每日会议
- 冲刺评审会
- 回顾会议

流程
1. 收集 product backlog
2. 选取一些 backlog 加入到 sprint 中
3. 开始执行 sprint，一个 sprint 即是一次迭代，每日举行站立会议，及时更新燃尽图
4. 交付验收 sprint
5. 总结 sprint

敏捷对团队要求
- 自主管理
- 自我组织：自己事情做完了还要帮助他人改进
- 多功能型：每个人全面负责，自己搞定规格说明书，和别人沟通，同时自己搞定测试

燃尽图帮团队判断
- 当前进度是否正常
- 是否可以延期
- 团队节奏是否稳定
- 是否存在阻塞问题

## 基于场景的建模
### 用例建模
**用例**
用于表示系统所提供的服务，描述参与者为了使用系统所提供的某一完整功能而与系统之间发生的一段对话（交互）
**场景**
场景是用例的实例化，从一个用例可以实例化出来多个用例场景，用例就是对全部场景的抽象

用例建模的步骤：
- 确定系统边界和范围
- 识别参与者
- 识别用例
- 对用例描述
- 定义用例之间关系
- 审核用例模型

#### **确定系统边界和范围**
**系统**：特指基于计算机的用于解决某个特定问题域的软硬件系统。
**系统范围**：系统提供的功能和任务、目标
**系统边界**：一个系统的所有元素与系统以外的事物的分界线

系统边界外部的事物统称为参与者（执行者，actor）

#### **识别系统的参与者**
系统之外，透过系统边界与系统进行有意义交互的任何事物
执行者不仅可以由人承担，还可以是其他系统、硬件设备、甚至是时钟等其他事物
其他系统：==比如 ATM 机系统中，银行后台系统是一个参与者==
硬件设备：系统要硬件设备交互，比如门禁系统中，ic 读卡器是个参与者
时钟：系统需要定时触发时，时钟是参与者

一个参与者可以启动多个用例，一个用例也可以被多个参与者启动![[Pasted image 20260518214146.png]]

#### 识别用例
**用例是一组动作序列的描述**，系统通过执行动作将对用例的参与者产生可以看到的结果

**用例实例**：系统执行一系列具体实际动作，这些动作生产特定参与者可观测的结果值
一个用例可有多个用例实例

==在 uml 中，每个用例有唯一名称，用椭圆形符号表示，用例名写在椭圆里面== ![[Pasted image 20260518214605.png]]
用例特性：
- 用例不自动执行，有参与者启动
- 用例表示一个完整的描述 ![[Pasted image 20260518214707.png]]
- 用例会提供可识别返回值 ![[Pasted image 20260518214727.png]]

**区分目标和步骤**
![[Pasted image 20260519091233.png]]
第一个是步骤，第二个是想要达成的目标

怎么来分用例的粒度，如果区分过细，会陷入功能分解
- 通过执行用例，参与者完成想完成的事（达到最终目的），并为参与者产生所需的价值
- 用例是系统级抽象级描述，不是细化的
- 划分粒度的标准方法是该用例是否完成了参与者的某个完整目的为依据的

**识别用例的方法**
- 系统能做什么
- 用户最关心系统哪些事件
- 用户自己要做什么
- 用户是否要在系统增删改查数据
- 信息从何而来到哪里去
- 文中描述寻找"动词+名词"

#### 对用例进行描述

| 描述项  | 说明                                   |
| ---- | ------------------------------------ |
| 用例编号 | 用例的唯一标识符，通常可以命名格式为：UC-xxx            |
| 用例名称 | 名称能体现用户的意图或用例的目标，“见名知义”，如“查询图书”      |
| 用例简述 | 对用例目标的概括性描述                          |
| 参与者  | 列出用例的参与者，尤其是主要参与者                    |
| 前置条件 | 启动该用例所需满足的前提条件；或执行该用例前系统必须所处的状态      |
| 后置条件 | 该用例执行完毕后，将执行的动作或用例；或用例执行完毕后系统可能处于的状态 |
| 基本流程 | 系统执行用例时具体的基本操作流程                     |
| 扩展点  | 操作流程中可能发生的其他情况（分支）                   |
| 异常点  | 操作流程发生被中断等异常情况                       |
| 补充说明 | 需要对用例进行补充性的说明事项                      |

#### 定义用例之间的关系
**包含关系**：借书用例行为包含校验借阅证行为和校验超期行为，否则借书用例不完整 ![[Pasted image 20260519101410.png]]
箭头指向被包含用例也称包含用例，箭头出发称为基本用例
- 一个用例功能太多需要用包含关系
- 多个用例用到同一个功能行为时，可以把它拿出为一个包含用例
![[Pasted image 20260519102010.png]]

**扩展关系**：只有在基本用例中的某种条件满足时才能执行，如果没有基本用例运行，扩展用例不能运行（就相当于一个分支）
校验是否超期用例--当超期才只执行罚款用例，否则不执行
罚款用例扩展了校验超期用例
![[Pasted image 20260519103023.png]]**泛化继承**：就是继承关系, 子用例继承父用例：当多个用例共同拥有一种类似的结构和行为的时候我们可以将它们的共性抽象成为父用例，其他的用例作为泛化关系中的子用例

**数据字典条目**：
DFD 元素基本信息
定义
使用特点（取值范围、使用频率、激发条件）
控制信息（来源、去向、访问权限）

**数据流条目**
名称：数据流名 (可以是中文名或英文名)
别名：名称的另一个名字
简述：对数据流的简单说明
数据流组成：描述数据流由哪些数据项组成
数据流来源：描述数据流从哪个加工或源点流出
数据流去向：描述数据流流入哪个加工或终点
数据量：系统中该数据流的总量。如考务处理系统中“报名单”的总量是 100000 张，或者单位时间处理的数据流数量，如 80000 张/天
峰值：某时段处理的最大数量，如每天上午 9：00 至 11：00 处理 60000 张表单
注解：对该数据流的其它补充说明

数据流组成是数据流条目的核心，它列出组成该数据流的各项数据
`运动员报名单＝队名＋姓名＋性别＋1｛参赛项目｝3`
当一个数据流组成比较复杂时，可以分解为几个数据流
`课程＝课程名＋任课教师＋教材＋时间地`
`时间地点＝｛星期几＋第几节＋教室｝`

**文件条目**
名称：文件名
别名：同数据流条目
简述：对文件的简单说明
文件组成：描述文件的记录由哪些数据项组成 (与数据流条目中的文件组成描述方法相同)
写文件的加工：描述哪些加工写文件
读文件的加工：描述哪些加工读文件
文件组织：描述文件的存储方式 (顺序、索引)，排序的关键字
使用权限：描述各类用户对文件读、写、修改的使用权限
数据量：文件的最大记录个数
存取频率：描述对该文件的读写频率
注解：对该文件的其它补充说明

**数据项条目**
名称：数据项名
别名：同数据流条目
简述：对数据项的简单描述
数据类型：描述数据项的类型，如整型、实型、字符串等
计量单位：指明数据项值的计量单位，如公斤、吨等
取值范围：描述数据项允许的值域，如 1.. 100

### 数据规范化
目的：
- 消除数据冗余
- 消除多义性
- 使关系的"概念"单一化：每个数据项只是一个简单的数或者字符串，而不是一个组项
- 方便操作（数据的增删改查）
- 使关系模型更灵活

如何规范化：将数据的逻辑结构总结成满足条件的二维表，比如：
![[Pasted image 20260519201952.png]]

三个实体：
学生 (学号，姓名，性别，年龄，年级，专业，籍贯)
教师 (职工号，姓名，年龄，职称，职务，工资级别，工资)
课程 (课程号，课程名，学分，学时，课程类型)

为了建立实体的关联，建立了两个关系：组成了数据库的模型
选课 (学号，课程号，听课出勤率，作业完成率，分数)
教课 (职工号，课程号，授课效果)

其中的关键字就能唯一标识一个元组

通常用范式来定义消除数据的冗余程度，第一范式（1 NF）数据冗余程度最大，第五范式（5 NF）数据冗余程度最小，但是范式级别越高，存储同样数据需要分解成更多表，所以一般第三范式

**第一范式**
每个属性都是原子值，比如学生 (**学号**，姓名，性别，年龄，年级，专业，籍贯)

**第二范式**
满足第一范式，而且每个非关键字属性都由整个关键字决定：选课 ( **学号**，**课程号**，听课出勤率，作业完成率，分数 )

**第三范式**
满足第二范式，每个非关键字属性仅由关键字决定，一个非关键字属性值不依赖于另一个非关键值属性值
比如：教师 (职工号，姓名，年龄，职称，职务，工资)  -----工资依赖于职称或职务，所以改成：
教师 (职工号，姓名，年龄，职称，职务，**工资级别**，工资) ，加了一个工资级别

# 7 软件设计
## 软件设计概念
设计：
- 坚固性
- 通用性
- 愉悦性

良好设计应具备的特征
- 必须实现所有包含在需求模型中的明确需求
- 对于编码测试以及维护而言，设计必须是可读的、可理解的指南
- 设计必须提供软件的全貌

设计质量指导原则
- 已经使用可识别的体系结构风格或模式创建；由展现出良好的设计特征的构件构成；能够以演化的方式实现，从而便于实现和测试
- 设计应该模块化
- 设计应该包含数据、体系结构、接口和构件的清晰表示
- 设计应导出数据结构
- 设计应导出显示独立功能特征的构件
- 设计应导出接口，降低了构件以及外部环境连接的复杂性
- 设计的导出应该根据软件需求分析过程
- 设计应使用能够有效的表示法来传达其意义

### **设计概念**
- 抽象--数据、过程、控制
- 体系结构--软件的整体结构
- 关注点分离--任何复杂问题在被分解为若干块后将更容易处理
- 模块化--数据和功能的分割
- 隐蔽--控制接口
- 功能独立--单一功能和低耦合
- 求精
- 方面--理解全局需求如何影响设计的机制
- 重构
- 面向对象的设计概念

**抽象**
- **数据抽象**：类似于弄成数据结构
- **过程抽象**：把这个过程细节抽象出来

**体系结构**
软件的整体结构和这种结构为系统提供概念上完整性的方式
- 结构模型
- 框架模型：提高设计抽象级别
- 动态模型：强调程序体系结构的行为方面
- 过程模型：系统必须提供的业务设计或技术流程设计
- 功能模型：系统的功能层次结构

**关注点分离**
将复杂问题做合理分解，再研究问题的不同侧面（关注点），最后综合各方面结构成一个整体的解决方案
通过将关注点分割为为更小的关注点，使得解决一个问题需要付出更少的工作量和时间

**模块化**
将设计划分成许多模块，构建软件所需的成本会随之降低
- 相互独立又相互关联
- 是系统分解和抽象的过程
模块是相对独立的程序体
- 单独命名，可以通过名字访问
- 是数据说明、可执行语句等程序对象的集合

模块无限制进行分化会导致开发工作量很大一部分来自模块之间的接口和集成，还有人之间沟通成本
==**所以要适度模块化**==
模块数量增加时，模块间关系也增加，接口和集成的工作量也增加

**信息隐蔽**
每个模块都尽量对其他模块隐藏自己的内部实现细节
典型的信息隐藏：面向对象的访问控制符 ![[Pasted image 20260519215626.png]]
- 降低副作用可能
- 减少局部对全局影响
- 突出控制接口处通信
- 阻止全局数据使用
- 促进封装
- 形成高质量软件

**功能独立**
开发具有“专一”功能和“避免”与其他模块过多交互的模块
- _内聚性显示了某个模块相关功能的强度（一个内聚的模块只用完成一件事）
- _耦合性显示了模块间的相互依赖性 (依赖模块之间的接口)

**方面**
考虑两个需求，A 和 B。“如果已经选择了一种软件分解[精化]，在这种分解中，如果不考虑需求 A 的话，需求 B 就不能得到满足” ，那么需求 A 横切需求 B

**重构**
检查现有设计的
- 冗余性
- 没有使用的设计元素
- 低效不必要的算法
- 拙劣的或不恰当的数据结构
- 其他不足，并通过修改获得更好的设计

**面向对象设计概念**
设计类
- 实体类（DAO）
- 控制类
- 边界类

## 用户界面设计
**黄金规则**
把控制权交给用户
减少用户的记忆负担
保持界面一致

**把控制权交给用户**
- 不强迫用户进入不希望的交互模式
- 提供灵活的交互
- 允许用户交互被中断或者撤销
- 当技能级别增长时可以使交互流线化并允许定制交互
- 使用户于内部技术细节隔离
- 设计应允许用户与出现在屏幕上的对象直接交互

**减少用户的记忆负担**
- 减少对短期记忆的要求
- 建立有意义的缺省
- 定义直观的快捷方式
- 界面视觉布局应基于真实世界特征
- 以不断进展的方式揭示信息

**保持界面一致**

#### 结构化详细设计
**如果一个程序的代码块仅仅通过顺序、选择和循环这三种基本控制结构进行连结，并且每个代码块只有一个入口和一个出口，则称这个程序是结构化的**

优点:
- 自顶向下逐步求精的方法符合人类解决复杂问题的普遍规律，因此可以显著提高软件开发工程的成功率和生产率。
- 用先全局后局部、先整体后细节、先抽象后具体的逐步求精过程开发出的程序有清晰的层次结构，因此容易阅读和理解。
- 仅使用单入口单出口的控制结构，使得程序的静态结构和它的动态执行情况比较一致。因此，程序容易阅读和理解，开发时也比较容易保证程序的正确性，即使出现错误也比较容易诊断和改正。
- 控制结构有确定的逻辑模式，编写程序代码只限于使用很少几种直截了当的方式，因此源程序清晰流畅，易读易懂而且容易测试。
- 程序清晰和模块化使得在修改和重新设计一个软件时可以重用的代码量最大。
- 程序的逻辑结构清晰，有利于程序正确性证明

# 软件测试
## 基本概念
狭义：为了发现软件错误而执行软件的过程
广义：在规定条件下对程序进行操作，发现程序错误、衡量软件质量、并对其能否满足设计要求进行评估的过程

**软件测试原则**
足够好原则：
- 不充分的测试是不负责任的
- 过分的测试是一种资源的浪费
- 如何界定什么样的测试是不充分的，什么样的测试是过分的

Pareto 法则
- 测试中 80%的错误可能来自 20%的代码
- 充分注意测试中的集群现象，经验表明，测试后程序残存的错误数目与该程序已发现的错误数目成正比

- 应当避免由程序员检查自己的程序
- 在设计测试用例时，应包括合理的输入条件和不合理的输入条件
- 严格执行测试计划，排除测试的随意性
- 妥善保存测试计划、测试用例、出错统计和最终分析报告，为维护提供方便
- ==检查程序是否做了应做的事仅是成功的一半，另一半是检查程序是否做了不该做的事==

**测试用例**
对特定软件产品进行测试任务的描述，体现测试方案、方法、技术和策略，包括测试目标，测试环境，输入数据，测试步骤，预期结果，测试脚本等，形成文档，例如: ![[Pasted image 20260520155916.png]]

**测试用例设计**
设计尽可能少的用例来发现尽可能多的错误
设计最有可能发现软件错误的测试用例，同时避免使用发现错误效果相同的测试用例
测试用例的设计方法大体可分为两类：白盒测试和黑盒测试

- 白盒测试（又称为结构测试）把测试对象看作一个透明的盒子，测试人员根据程序内部的逻辑结构及有关信息设计测试用例，检查程序中所有逻辑路径是否都按预定的要求正确地工作,白盒测试主要用于对模块的测试.
- 黑盒测试（又称行为测试）把测试对象看做一个黑盒子，测试人员完全不考虑程序内部的逻辑结构和内部特性，只依据程序的需求规格说明书，检查程序的功能是否符合它的功能需求,黑盒测试可用于各种测试.

## 软件测试的分类
**按测试方法分类**
- 静态测试：不需要执行程序
- 动态测试：选择用例运行程序

**按测试过程分类**
- 单元测试：对程序的模块或构件
- 集成测试：对集成的软件系统
- 确认测试：根据软件需求规约对集成的软件进行确认，揭露不符合需求规约的错误
- 系统测试：将它集成到计算机系统中进行，揭露不符合系统工程中对软件要求的错误

**按测试目的分类**
功能测试、健壮性测试、接口测试、性能测试、强度测试、压力测试、用户界面测试、安全测试、可靠性测试、安装反安装测试、文档测试、恢复测试、兼容性测试

### **回归测试**
重新运行已经测试过得子集，确保变更没有引发非预期副作用
回归测试可以手动进行，通过重新运行一部分测试用例或者全部测试用例，也可以使用自动的捕获/回放工具

### **冒烟测试**
对产品进行每日构造
步骤：
- 已经被翻译为代码的软件构件被集成到构造（ “build” ）中。一个构造包括所有的数据文件、库、可重用的模块、以及工程化的构件，其中一个构件需要实现一项或多项产品功能
- 设计一系列测试来揭示错误，使得此构造不能正确地执行其功能。
- 将此构造与其他构造集成在一起，每天都对整个产品（以其当前的形式）进行冒烟测试
